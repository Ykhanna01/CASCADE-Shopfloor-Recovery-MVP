# Build CASCADE — Alexa+ Hackathon MVP

Build the initial working version of CASCADE, an Alexa+-style Shopfloor Recovery Agent for small custom-production workshops.

## Objective

Demonstrate how a voice-first AI agent responds when a supplier delay disrupts multiple production orders that share inventory, machine capacity and delivery deadlines.

This is a hackathon MVP, not a full manufacturing ERP.

## Technical requirements

- Use TypeScript and a lightweight React + Vite frontend.
- Implement a real self-hosted MCP server using the official TypeScript MCP SDK.
- Support Streamable HTTP and target the hackathon-required MCP specification version 2025-11-25.
- Keep the recovery calculations deterministic and separate from the conversational AI layer.
- Make the application runnable locally in Replit and suitable for deployment to a public HTTPS endpoint.
- Include a clear README, environment-variable example, tests and an open-source license.
- Do not require access to Amazon's private Alexa+ preview tools.
- Build a browser-based Alexa+-style simulator that calls the same MCP tools as the test client.

## Demo scenario

Create a fictional custom-production workshop with:

- 8 customer orders with priorities, deadlines and quantities.
- Shared raw materials and limited machine capacity.
- Supplier delivery dates and alternative sourcing options.
- Production tasks with dependencies, durations and costs.
- Explicit penalties or costs for late delivery, expedited materials and rescheduling.

The initial state must be internally consistent and deterministic.

The user says:

"Our plywood shipment is delayed by two days. Can we still deliver the Palmer order on Friday without making our other customers late?"

The application must:

1. Identify all affected orders and dependencies.
2. Show the affected production graph.
3. Calculate at least two feasible recovery alternatives when feasible.
4. Compare total recovery cost, orders delivered on time, late orders and remaining risks.
5. Explain why each plan is feasible or infeasible.
6. Ask for approval before consequential changes.
7. Update the simulated production state after approval.
8. Recalculate the schedule and show the verified result.
9. Maintain an auditable action history.

Use honest labels for simulated data. Never claim a real supplier, customer or production system was contacted.

## Initial MCP tools

- get_shop_state
- simulate_disruption
- analyze_impact
- propose_recovery
- approve_recovery
- execute_recovery
- verify_recovery

Use typed input schemas, validate arguments and return structured outputs. Keep tool names and responsibilities clear.

## User interface

Build a polished, modern operations dashboard with:

- A conversational assistant panel.
- An interactive production dependency graph.
- An at-risk orders panel.
- Side-by-side recovery plan cards.
- Explicit approval controls.
- A live action timeline and verification results.

Use a coherent visual design, strong information hierarchy and realistic sample data. Do not spend the first milestone on elaborate animations.

## Reliability requirements

- Write tests for the dependency engine and recovery calculations.
- Test valid and invalid tool inputs.
- Ensure the approval step is required before executing a recovery plan.
- Handle infeasible plans honestly.
- Make repeated tool calls safe and prevent duplicate execution.
- Ensure the displayed outcome agrees with the persisted simulated state.
- Provide a simple deterministic fallback for the demo if an external AI service is unavailable.

## First milestone

Do not attempt every feature at once. First deliver:

1. A runnable MCP server over Streamable HTTP.
2. A valid workshop state.
3. A working disruption tool.
4. A deterministic impact analysis.
5. Automated tests proving the results.

After this passes, build the recovery optimizer and then connect the simulator UI. Prioritize a reliable end-to-end demo over feature count.
